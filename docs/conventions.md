# Правила работы команды с Git

Документ составлен Сеньором по итогам обсуждения в команде. Правила обязательны для всех участников; Сеньор следит за их выполнением при проверке веток и слиянии.

## 1. Проект и окружение

- Вариант тестового проекта — **TopDown** (`Assets/IndieMarc/TopDownDemo`, основная сцена `TopDownDemo.unity`).
- Папка `Assets/IndieMarc/PlatformerDemo` не используется и исключена через `.gitignore`.
- Версия Unity у всех участников и в CI — **6000.4.0f1** (см. `ProjectSettings/ProjectVersion.txt`). Открывать проект в другой версии и коммитить изменённый `ProjectVersion.txt` нельзя: разные версии по-разному сериализуют сцены и префабы.

## 2. Ветки

- `main` — стабильная ветка, каждый push в неё собирается в GitHub Actions.
- Рабочие ветки: `<тип>/<роль>-<тема>` — латиницей, в нижнем регистре, слова через дефис.
  - `<тип>`: `feature` — новая функциональность или изменение уровня, `fix` — исправление, `docs` — документация, `ci` — настройка сборки.
  - Примеры: `feature/senior-visuals`, `feature/junior-gameplay`, `fix/devops-level-bounds`.
- Изменения сцены выполняются только в рабочих ветках. Документацию этапа 2 допускается коммитить прямо в `main`, по очереди.
- Сливает ветки в `main` Сеньор командой `git merge --no-ff <ветка>`. После слияния ветка удаляется локально и на `origin`.

## 3. Формат коммитов

- Язык — **английский**.
- Заголовок — по [Conventional Commits](https://www.conventionalcommits.org/): `<type>(<scope>): <subject>`
  - `type`: `feat`, `fix`, `docs`, `test`, `ci`, `chore`, `refactor`, `style`;
  - `scope` (необязательно): `visuals`, `gameplay`, `scene`, `project`, `vcs`, `ci`, …;
  - `subject`: повелительное наклонение, со строчной буквы, без точки в конце, не длиннее 72 символов.
- Описание (необязательно) — после пустой строки: что изменено и зачем, можно списком.
- Коммит слияния — стандартный заголовок Git `Merge branch '<ветка>'`, а в описании — какие были конфликты и как они разрешены.

Пример:

```
feat(visuals): tune scene lighting and camera field of view

- Directional light: cool moonlight color, intensity 0.65
- Main Camera: field of view 60 -> 65
```

## 4. Содержание коммитов

- Коммиты **атомарные**: один коммит — одно логическое изменение. Запись в `docs/changelog.md` идёт в том же коммите, что и описываемое изменение.
- После каждого коммита проект должен открываться в Unity без ошибок.
- Не коммитить сгенерированные и временные файлы: `Library/`, `Temp/`, `Logs/`, `UserSettings/`, `Assets/_Recovery/` (резервные сцены после падения Unity), сборки.

## 5. Документация

- Документы лежат в `docs/`, имена файлов — в нижнем регистре с расширением `.md` (`structure.md`, а не `structure.MD`): Windows не различает регистр в именах файлов, а Git различает.
- `docs/changelog.md` — изменения уровня в формате `- [Что изменено] — [Зачем]`, у каждого участника свой раздел (`## Изменения Джуниора`, `## Изменения Сеньора`).

## 6. Слияние сцен Unity

Для конфликтов в `.unity` и `.prefab` рекомендуется Unity Smart Merge (UnityYAMLMerge). Он входит в состав редактора и разбирает файл по объектам сцены, а не по строкам. Настройка (путь замените на свой):

```
git config merge.tool unityyamlmerge
git config mergetool.unityyamlmerge.trustExitCode false
git config mergetool.unityyamlmerge.cmd "'<путь к Unity>/Editor/Data/Tools/UnityYAMLMerge.exe' merge -p \"\$BASE\" \"\$REMOTE\" \"\$LOCAL\" \"\$MERGED\""
```

После этого при конфликте запускается `git mergetool`. Результат слияния обязательно проверяется открытием сцены в Unity.
